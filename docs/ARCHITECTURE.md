# Finding your way around the quiz application

See [deployment and AI pipeline diagrams](DIAGRAMS.md) for the visual overview.

Edit Python in `markdown_quiz/` and TypeScript in `obsidian-markdown-quiz/src/`.
The plugin's bundled backend, `main.js` files and `dist/` are generated by the
normal build/package scripts. JSON under data directories is study state.
Paths below are relative to the project root or their named source directory.
Folders group related files; calls still go directly to the implementation.

## Where to look

| Question | Implementation |
| --- | --- |
| Where is Markdown parsed? | `notes/parser.py`: `scan_vault` reads notes; `extract_frontmatter` preserves physical lines; `parse_markdown` walks fences, scoped tags and both term formats. |
| Where are questions selected? | `quiz/selection.py`: `eligible` chooses active source records; `filter_questions` applies tags, dates, source, due state and explicit IDs. |
| Where is a quiz started? | `quiz/engine.py`: `QuizEngine.start` validates the selection, orders the queue and prepares the first question. |
| Where are retries and queue changes handled? | `quiz/engine.py`: `answer`, `advance`, `skip`, `regenerate_question` and `configure_coding_question`. `operate` is the action list. |
| Where are multiple-choice answers created? | `quiz/term_quiz.py`: `build_question` reuses cached distractors or requests them, builds forward/reverse choices and shuffles them. |
| Where is an answer graded? | Multiple choice: `engine.answer` compares server-owned answer IDs. Interactive code: `questions.grade_coding` reconstructs protected blanks and compares sandbox output. CLI code: `code_quiz.grade_answer`. |
| Where is progress stored? | `notes/storage.py` loads/validates records, synchronizes source changes and writes JSON atomically. `backend.py` owns the loaded collections; `quiz/engine.py` owns persisted sessions. |
| Where is spaced repetition calculated? | `quiz/spaced_repetition.py`: `record_answer`, `review_time` and `priority`; `engine.record_attempt` supplies shared attempt metadata. |
| Where does Python execute? | `services/sandbox.py`: restricted Docker containers only. `services/libraries.py` builds optional library images. |
| Where are models contacted? | `services/ollama.py`: local JSON generation and provider selection. `services/cloud.py`: HTTPS compatible remote service, with request-scoped credentials. |
| Where are HTTP routes? | `api.py`: authentication/vault resolution in the handler, endpoint list in `dispatch`, legacy quiz translation in `quiz`, named sync/reset operations. |
| Where is the Obsidian UI? | `views/QuizView.ts` for the sidebar; `views/inlineCodeQuiz.ts` for widget placement; shared question/recovery controls in `views/questionRenderers.ts`, regeneration controls in `settings/modelPicker.ts`. |

## Request and data flow

Both sidebar and inline practice use `SessionController` in `quiz/session.ts`. Views
subscribe to it; closing a view does not discard a quiz. It assembles session IDs,
question IDs, selection/model options and ephemeral credentials, then calls
`QuizClient`. The client connects the active vault, sends authenticated requests,
deduplicates in-flight work and validates responses. The HTTP handler resolves
the vault before calling `QuizAPI.dispatch` and `QuizEngine.operate`.

For a **multiple-choice quiz**:

1. `start` calls `selection.filter_questions`, shuffles or orders the source IDs
   and creates one `SessionState`.
2. `prepare_question` rescans the selected source and calls `term_quiz.build_question`
   directly. The builder reuses matching cached distractors (including identical
   material in other notes) or requests Ollama/the configured remote provider.
3. The engine assigns opaque answer and question IDs and snapshots the private key.
   The public response hides that key, the correct index and explanation.
4. `answer` validates the current source and answer ID. A wrong first attempt keeps
   the same choice order; the second attempt completes the question. Request IDs
   make retransmissions idempotent.
5. `record_attempt` records shared history. A final answer calls the scheduler,
   saves progress and updates the session summary. `advance` prepares the next item.

For a **coding quiz**:

1. The same `start`, filter pipeline, session, queue and transition methods apply.
2. `questions.coding_instance` varies only safe numeric demonstration inputs using
   Python ASTs, builds one or more editable blanks, and verifies original and
   reconstructed output in Docker. Programs needing stdin pause for program input.
3. Silent/invalid sources are removed and the requested count is backfilled when
   possible. Rejected source code does not count as a student attempt. A silent
   program with no blank candidates (such as `pass`) is classified as silent too.
4. The server reconstructs only the blank values submitted by the client.
   `grade_coding` reports syntax/runtime/output errors, timeouts and output limits;
   infrastructure failures do not penalize the student.
5. Wrong coding answers remain retryable. Success or an explicit skip uses the
   same attempt/history/scheduler path as multiple choice. Drafts persist with the
   session; the question retains its original sandbox image when libraries change.

The terminal UI deliberately keeps its established interaction: weighted source
selection, one-answer multiple choice and LLM-generated one-blank code exercises.
It shares parser, storage, tag filtering, term construction, scheduler, providers
and Docker execution, without imposing interactive HTTP retry rules on the CLI.

## Persistent objects and compatibility

`ParsedTerm` and `ParsedCode` in `notes/parser.py` name source fields. Storage adds
`ProgressRecord` fields such as mastery, counters, history and next review.
`QuizFilters` in `quiz/selection.py` names accepted selection/model options.
`SessionState` in `quiz/engine.py` names the private persisted session shape.
`types.ts` centralizes frontend settings, actions, answers and API responses.
Typed dictionaries document the existing JSON objects without serialization
conversions or a data migration. `Settings` and sandbox `RunResult` remain dataclasses.

Term identity still hashes source path plus normalized term; code identity still
uses source path, normalized Python and duplicate occurrence. Generated question
IDs are separate from learning-source IDs. Changing a source invalidates a stale
question; renaming a note moves its progress to the new source identity. Notes are
never edited by quiz operations. Managed servers operate on uploaded snapshots.

The documented `markdown_quiz.backend` and `markdown_quiz.config` imports and all
launch commands remain available. Internal modules now live in the folders above.

`terms.json`, `code_quizzes.json`, `settings.json` and `sessions.json` retain their
formats. Sessions retain the 256 most recently used entries. Atomic writes and
refusal to overwrite corrupt data are unchanged. Legacy `/quiz/term/*` and
`/quiz/code/*` endpoints adapt to the same engine. Documented backend operations
and tested filter re-exports remain available. The engine uses the descriptive
method names listed above; uncalled aliases of the former names were removed.
API keys remain request-scoped and are never serialized.

## Docker and deployment

`sandbox.run_in_sandbox` creates an unprivileged, read-only, network-disabled
container with time, memory, CPU, process and output limits. It attaches stdin,
checks the actual container exit state and forcibly removes the container during
cleanup. There is no host-Python execution fallback. Optional packages install
as binary wheels in a dedicated Docker image.

Local Obsidian startup remains hidden on Windows and only restarts an identified
local backend. Managed mode requires bearer authentication and derives snapshot
directories from opaque vault keys. Compose runs Ollama separately; only the API
container receives the Docker socket. Student containers receive no vault mount.
`scripts/package_release.py` copies canonical Python and compiled frontend assets
into the installable plugin and creates all five release ZIPs.

## Architecture comparison

| Path / measure | Before | After |
| --- | --- | --- |
| MC construction from API, excluding provider transport | API → engine → backend → term builder: 4 modules | API → engine → term builder: 3 modules |
| Filter ownership | `quiz/questions.py` plus `quiz/term_quiz.py`, mixed with generation | `quiz/selection.py`; old locations directly re-export the functions |
| Interactive coding request | API → engine → questions → sandbox: 4 modules | Same 4 modules, with filtering removed from coding generation |
| Session action dispatcher | 79 lines mixing transitions and coding configuration | 33 lines delegating to named operations in the same file |
| HTTP endpoint dispatcher | 108 lines including sync/reset implementations | 46 lines with named sync/reset operations in the same file |
| Frontend recovery and regeneration | Repeated in sidebar and inline rendering | One implementation per responsibility |

The refactor reduces the number of responsibilities to trace, rather than forcing
fewer files. See `REFACTOR_NOTES.md` for the change inventory, baseline findings,
verification results and remaining technical debt.
